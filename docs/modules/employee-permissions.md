# Tres niveles y permisos de empleados

El superadministrador pertenece a la plataforma y exige TOTP. El administrador titular es el owner de una panadería; paga y renueva una única suscripción para el negocio. Los empleados son miembros no-owner, no pueden invitar, retirar a otros, modificar permisos, administrar sucursales ni gestionar la suscripción. No hay alta de un segundo titular. Internamente se conserva admin como rol de compatibilidad de empleado; no equivale al administrador titular ni da permisos por sí solo. Los antiguos roles operativos se convierten a permisos iniciales compatibles; la instancia no tenía membresías al preparar esta migración. Las invitaciones antiguas se convierten de forma equivalente.

Permisos configurables por titular: inventory (catálogo, movimientos, mínimos, mermas), recipes (versionar recetas), production (confirmar lotes), purchases (proveedores y recepciones), sales (registrar ventas), prices (configurar precios), cash (abrir/cerrar caja, ingresos/egresos), reports (consultar reportes). La UI permite asignarlos al invitar y editar después. Las invitaciones sin permisos no conceden facultades. La asignación se verifica en la base con sesión válida, pertenencia y bloqueo por negocio; el usuario no puede editar sus propios permisos. No se amplían permisos con suscripción inactiva. Revocación y reducción se permiten aun vencida.

Los RPC de mutación validan permisos en las funciones privadas; las escrituras directas de catálogo/proveedores/sucursales tienen políticas restrictivas. Los movimientos internos de compras/producción usan una primitiva privada no ejecutable por authenticated. Las políticas de lectura filtran por módulo y dependencias compartidas. Por ejemplo producción consulta catálogo, receta y stock; ventas consulta productos, precios y caja. Caja y reportes requieren información de ventas, y reportes accede a compras y lotes de producto terminado. La ocultación de navegación no equivale a confidencialidad de columnas: datos necesarios para operar pueden consultarse vía API incluso si no se muestra otra vista. Pendiente separar columnas sensibles, limitar por sucursal y auditar historial de cada cambio de permisos (se conserva último editor y fecha). Las modificaciones en otra sesión se aplican en servidor inmediatamente al siguiente acceso; el menú refleja cambios al actualizar o ingresar de nuevo. Mantener bakery_private fuera de la Data API. No se modifica el esquema de suscripciones ni se añade servicio de pago.
